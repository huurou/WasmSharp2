# ブリーフ: runtime-performance

## 課題

Core 2.0の固定公式スイートによる受入まで進んだ一方、WasmSharp2には繰り返し比較できる性能測定基盤と基準値がない。C#から埋め込んで使う際の実行時間とメモリ割り当てを把握し、寄与の大きい部分を改善したい。

**実行時間の短縮とメモリ割り当ての最小化を同格の目標とする。** 時間がほぼ変わらなくても、同じ処理の割り当て量が減れば改善として評価する。割り当て量を時間の補足指標だけにせず、測定・原因調査・改善選定・完了確認の全段階で扱う。

## 現状

- .NET10上のC#製インタープリターで、公開APIは`Decode → Validate → Instantiate → Invoke`を分離している。検証と線形化を同一パスで行い、生成された単一のswitch実行ループを使う。
- 既存8仕様の実装と公式受入の記録がある。固定スイートの最新受入は147入力・53,907commandで、52,830件がpassed、1,077件がout_of_scope、失敗・未対応・前提不成立・回帰・欠落が0件。これは[既存の受入記録](../simd/acceptance.md)であり、今回の調査で再実行した結果ではない。
- `src`・`tests`・`tools`・CIの探索ではBenchmarkDotNet参照や性能測定プロジェクトは見つからなかった。性能上の主要な原因や改善量は未測定。
- 最外側のWasm呼び出しでの実行コンテキストと配列の生成、結果コピー、host callbackへの引数コピー、間接callの型照合、ページ単位のmemory処理、SIMDのlane処理が観測候補にある。構造から挙げた候補であり、改善対象や方式はまだ決めない。

## 望む結果

1. 10〜15ケース程度の代表処理について、時間・managed割り当て量・GCと測定条件を保存し、変更前後を再現可能な方法で比較できる。
2. 時間または割り当てへの寄与が大きい1〜3箇所を測定から選び、改善する。基盤の追加だけで完了とせず、少なくとも1件の時間短縮または割り当て削減を、同じ入力・同じ条件で確認する。
3. 他の代表ケースやもう一方の指標への影響を示し、総合値で大きな悪化を隠さない。再利用による割り当て削減では、保持メモリと参照の寿命への影響も確認する。
4. 公開API、Core 2.0の意味論、診断互換性を維持し、既存テストと固定公式スイートで回帰がないことを確認する。

## 方針

### 選択した進め方

2026-10-22のdiscoveryで、新しい単一仕様`runtime-performance`を作る方針と、**A案: 全体を測って主要箇所を改善する**方針を選択した。準備処理・呼び出し・計算・メモリ・SIMDを少数のケースで代表させ、上位の原因を確認してから変更する。規模は中を想定する。

短いInvokeだけに集中するB案は着手を小さくできるが、測定前に優先領域を狭めるため採用しない。他ランタイムとの比較も初回から含むC案は、素材・実行方式・設定を揃える作業が増えるため後続とする。[調査ノート](../../../docs/research/wasm-performance-measurement.md)の先行区切りを踏まえ、今回は基準値の取得に加えて改善成果まで含める。

### 測定と改善

- `tools/WasmSharp.Benchmarks/`を配置候補とし、公開APIを使う独立した測定プロジェクトにする。BenchmarkDotNetの時間測定と`MemoryDiagnoser`を土台にする。
- 初期環境は現在のWindows x64/.NET10とし、単一スレッドの同期利用を測る。Release・デバッガなしで、SDK/runtime・CPU・OS・GC/JIT・電源条件等を記録する。
- 主指標はケースごとの実行時間とmanaged bytes/op。GC回数も記録する。累積割り当て量は、保持量・ピーク量・nativeメモリ量やguestの既存線形メモリ内の利用量とは区別する。
- まず同じ版の再測定で時間のばらつきと割り当て量の安定性を把握する。その後、改善に着手する前に、対象ケース・操作単位・狙う指標・目標と悪化の判断幅を記録する。一律の削減率や全操作の割り当て0を事前には要求しない。
- 時間と割り当ての原因を必要なケースでプロファイルし、上位1〜3箇所を選ぶ。診断を有効にした測定は通常の比較と分ける。コンテキストの再利用、コピー削減、SIMDの変更等は、測定で必要性が分かった場合に検討する。
- 責務・境界・所有権を保つ形に整理してから最適化する。返却値の独立性や同期再入を崩す共用バッファ化、検証・境界検査の省略を性能改善として採用しない。
- 変更ごとに同じ素材で比較し、最終的に代表ケース全体を再測定する。再利用やプールを導入する場合は、必要な保持量の観測を追加し、長大な配列や参照を不要に保持していないか確認する。

### 初期ケースと測定区間

次の分類から合計10〜15ケース程度を選ぶ。分類とパラメーターの全組合せを作る計画ではなく、素材と期待結果を固定する段階で最終一覧を決める。

| 分類 | 代表させる処理 |
| --- | --- |
| 公開呼び出し | 短いInvokeの結果0個・1個・複数個 |
| guest計算 | 整数・浮動小数点のループと分岐 |
| 関数呼び出し | 直接call・間接call・host callback |
| メモリ | 配列走査、copy/fill。必要な原因調査でページ境界やgrowを追加 |
| SIMD | 同じ入力・同じ結果のscalar処理とSIMD処理 |
| 準備処理 | 大きさや命令・dataの比率が異なるmodule |
| 複合処理 | 小さなWATだけに偏らない、C/Rust由来の計算kernelを1〜2件 |

初期の測定区間はDecode、Decode+Validate、Instantiate、定常Invokeとする。ファイルI/OとWAT変換、素材のコンパイルは測定外に置く。Instantiateは検証済みmoduleから新しいinstanceを生成し、定常Invokeはmodule・instance・export・引数を準備して公開呼び出しを測る。短いInvokeのホスト側反復と長いguestループは分ける。

`Validate()`は検証済みmoduleで処理を省略するため、同じ検証済みmoduleの反復をValidateの測定にしない。単体測定が必要なら毎回未検証の入力を用意する。DecodeとDecode+Validateの平均値の差を、精度の保証されたValidate単体の値として扱わない。

結果は測定中に消費し、期待値との照合は計時外で行う。測定前と反復後の正しさを確認し、可変memory・table・global等の状態復元位置を定める。初回だけ正常な処理、反復で処理量が減る入力、上限到達後の失敗したgrowを正常処理の性能として集計しない。trapや結果不一致は測定失敗として扱う。

### 保存と受入

時間と割り当ての個別結果、ばらつき、詳細JSON/CSV、実行コマンド、HEADと未コミット差分、ツール版、素材・入力のhash、期待結果を保存する。性能の基準値は新しい測定で上書きせず、公式適合検証のbaselineとも分ける。

改善の受入は、時間短縮または割り当て削減を再現でき、両指標と他ケースへの影響を説明できることとする。時間が同等で割り当てが減る変更も対象とする。トレードオフがある場合は事前に定めた判断幅に照らし、片方だけを提示して採用しない。数値目標と詳細な測定手順は、仕様化と基準値取得を通じて確定する。

ランタイム変更では警告・エラー0のReleaseビルド後に関連テストを実行し、完了確認では現行手順による固定公式スイート全体の実行・baseline比較・verifyを行う。比較前のbaseline更新や、期待値・対象集合の変更で回帰を隠さない。

## 範囲

- **対象**: 少数の固定素材と期待結果、公開APIによる測定基盤、時間と割り当ての基準値、必要な原因調査、主要1〜3箇所の改善、変更前後の比較、Core 2.0の回帰確認、再実行手順。
- **対象外**: Core 3.0、WASI、JIT/AOTやregister IRへの全面変更、既存エンジンへの実行委譲、公開APIの破壊的変更、測定専用の公開API、並行実行保証、全opcodeの個別ベンチ、外部スイート全体の移植。
- **後続候補**: 他ランタイムとの比較、プロセス起動から最初の結果までの独立測定、環境を揃えた性能CI。初回から共有CIへ一律の速度しきい値を導入しない。

## 責務の接点

- 測定ツールは素材・入力・期待結果・反復状態・測定区間・出力を所有し、ランタイムには公開APIで接続する。公式テストランナーへ性能測定の責務を加えない。
- ランタイムの変更は既存のmodule検証、実行境界、スタック、memory/table、命令処理の各所有箇所へ置く。測定ツールから内部状態を操作する専用hookは追加しない。
- 実行コンテキストや結果保持の変更では、物理的なバッファ再利用と論理的な呼び出し状態を区別する。後続呼び出しからの結果の独立、ホスト例外、同期再入、最外側の深さ上限、終了後の状態復元を維持する。

## この仕様が所有しないこと

命令の意味論、import/exportの同一性、公開APIの段階別契約、公式スイートの判定・baseline管理は既存仕様が所有する。数値結果、NaN・符号付きゼロ、参照の同一性、範囲外trap、失敗時の部分更新禁止、診断選択を性能上の都合で再定義しない。

## 上流・下流

- **上流**: 完了済み8仕様。各機能と公開APIを測定に使い、`test-suite-runner`と現在の固定公式素材・baselineを回帰確認に使う。
- **下流**: 今後の局所的な性能改善と将来のCore 3.0計画。同じCore 2.0素材を性能の変化の確認に利用できるが、他環境・他エンジンへの順位や未対応機能への性能を保証しない。

## 既存仕様との関係

| 仕様 | 本仕様との接点 |
| --- | --- |
| `runtime-foundation` | 4段階API、値と型、検証・線形化、実行ループと失敗分類 |
| `host-linking` | Invoke、結果所有、関数呼び出し、同期再入、importと共有リソース |
| `test-suite-runner`・`test-suite-conformance` | 固定スイートによる回帰確認、診断互換性の維持 |
| `numeric-control` | 数値・分岐・ループと共有スタック |
| `linear-memory` | load/store、bulk memory、ページ処理と初期化 |
| `tables-references` | 間接call、table、参照の同一性と寿命 |
| `simd` | v128とSIMD命令の意味論、scalarとの比較ケース |

既存仕様の完了状態と承認済み契約は維持する。今回の測定・改善の要件と受入を新仕様へまとめ、過去の受入記録を書き換えない。

## 制約と確認事項

- BenchmarkDotNetは.NET10対応を[0.15.0の履歴](https://benchmarkdotnet.org/changelog/v0.15.0.html)で確認でき、初期固定版の候補を[0.15.8](https://www.nuget.org/packages/BenchmarkDotNet/0.15.8)とする。導入・ビルドは未実施であり、実装時にこのリポジトリの設定で別プロセスの最小ケースが動くことを確認する。
- 0.15.8の.NET10向け割り当て測定は、プロセス内のmanaged累積割り当て差分から操作当たりの量を算出する。保持量やピーク量の代用にはしない。[固定版のGcStats](https://github.com/dotnet/BenchmarkDotNet/blob/v0.15.8/src/BenchmarkDotNet/Engines/GcStats.cs)
- 外部素材は固定commit・コンパイラ・flag・hash・由来・ライセンス表示を記録する。wasmi系素材は初期候補だが、個別のCore 2.0 feature・import・期待値を確認して採用する。起動用のWASI stubを計算の正しさ確認なしにInvokeへ流用しない。[素材一覧](https://github.com/wasmi-labs/wasmi-benchmarks#execution-benchmarks)、[MITライセンス](https://github.com/wasmi-labs/wasmi-benchmarks/blob/main/LICENSE-MIT)
- C/Rust生成物に含まれる依存コードの条件も採用時に確認する。PolyBenchは任意候補に留め、MIT素材と同じ条件とは扱わず、採用する原配布物のライセンスを確認する。[作者の配布先](https://sourceforge.net/projects/polybench/files/)
- 現時点で重大な採用阻害要因は確認されていないが、素材の最終選定、ビルド・実行互換性、性能の基準値と改善量は未確認。今回のdiscoveryは性能測定や実装検証の完了を意味しない。
- 要件・設計・タスクの段階で測定条件と受入を具体化する。文書は日本語とし、C#変更時は既存規約に従う。Gitのステージング・コミット等はこの方針選択に含めない。
