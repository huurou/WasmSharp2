# 検証と線形化を一体にし、単一の線形インタープリタで実行する

2026-09-06のdiscoveryで、検証しながらフラットな実行コードを生成し、単一のswitchループで実行する方式を採用した。入れ子の命令ツリーを実行する案ではbrの完了値を外側フレームへ伝播する規則が必要になるため、型スタックから得る分岐情報を`(targetPc, stackHeight, keepCount)`に落とす方式を選ぶ。検証と線形化を別パスにして型スタックを二度処理する案も避け、検証済みモデルと実行モデルを二重保持しない。

opcode・名前・即値形状・スタック効果・検証規則・実行ハンドラは1テーブルを唯一の定義元とし、SIMDも同じ定義元と実行機構へ追加する。

受け入れる不利益は、実行時の制御構造を単純にする代わりに、仕様に記述されたblock/loopの入れ子構造と実行表現との直接的な対応を失うことである。仕様との照合やデバッグでは線形化による変換を一段たどる必要があり、実行コードのpcだけでは元のWasmの構造やバイトオフセットを特定できない。元の位置を示す診断には対応情報の保持が別途必要になり、その生成・保持にもコストがかかる。

命令テーブルとswitchの同期方法、前方分岐の解決、スタック基準、診断に必要な元位置情報の粒度と保持方法は後続のdesignで確定する。pcから元のバイトオフセットへの対応表はその選択肢であり、このADRで専用の表構造まで指定しない。この選択はDecodeで得る入力表現の存在や、意味論をまとめる通常の補助メソッドまで禁止するものではない。

trapの伝播方式は実行表現と独立に見直せる判断として、[ADR 0004](0004-trap-result-propagation.md)へ分離した。
